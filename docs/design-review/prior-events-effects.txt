## Hooks should observe facts, not secretly control execution

For version one, hooks should be asynchronous reactions to events that have already happened.

```text
agent.completed
    fact

flow.failed
    fact

artifact.created
    fact
```

A hook should not be able to reinterpret `agent.completed`, prevent it from happening, or silently alter the result.

That gives a clear boundary:

```text
Event hook
    Observes and reacts.

Flow graph
    Controls execution.

Host effect
    Performs an operation and returns a result.

Agent implementation
    Controls provider-specific behavior.
```

When behavior must occur before an Agent runs, it belongs in:

- a preceding Node;
- the Agent subclass;
- an explicit approval effect;
- or the containing Flow.

It should not be hidden in a global “before Agent” hook.

This prevents invisible control flow and deadlocks.

## Hooks should not imply ordering

Several hooks may subscribe to the same event:

```text
agent.completed
├── update monitoring artifacts
├── create an orchestrator checkpoint
├── update the Kanban card
└── notify a human
```

Those reactions should be independent by default.

Jig should not promise that one runs before another. When ordering is required, put the operations into one Flow:

```text
Update monitoring
    ↓
Update Kanban
    ↓
Checkpoint
    ↓
Notify
```

A useful rule is:

> **Hooks fan out. Flows sequence.**

That keeps sequencing visible in the graph rather than depending on registration order.

## One normalized event fabric

All sources should feed the same event system.

```text
Local filesystem watcher
    jig.events.emit(...)

Jig Agent node
    emits agent.* events

Caskada observer
    emits caskada.* events

FLOW protocol process
    sends flow/event notifications

Task scheduler
    emits task.* and flow.* events

User hook or custom integration
    emits arbitrary namespaced events
```

A basic event envelope could be:

```ts
interface JigEvent<T = unknown> {
  id: string;
  type: string;
  at: string;

  taskId?: string;
  invocationId?: string;

  origin?: {
    kind:
      | "system"
      | "hook"
      | "flow"
      | "agent"
      | "user";

    id?: string;
    flow?: string;
  };

  causedBy?: string;
  correlationId?: string;
  depth: number;

  data: T;

```

The core should not define every possible event name.

It should define:

- the envelope;
- durable publication;
- delivery;
- causality;
- cancellation;
- diagnostics.

Projects, Agent implementations, Flow runtimes, and integrations may introduce namespaced events.

A Flow triggered by a hook should receive:

```text
+

```

For native Caskada execution, Jig can place the event in the root invocation memory:

For FLOW protocol execution, it becomes an optional part of `flow/run`:

## Durable delivery belongs in the kernel

Fully editable hooks do not mean the underlying event system should be left to every Starter to reimplement.

The core should guarantee:

1. The event is persisted before hooks receive it.
2. Every event has a stable ID.
3. Every hook has a stable ID.
4. Delivery status is recorded.
5. A crash may produce redelivery, but not silent loss.
6. Duplicate delivery can be recognized.
7. One failing hook does not erase the event or silently prevent unrelated hooks.
8. Causal depth is tracked to prevent uncontrolled loops.

The realistic delivery guarantee is **at least once**, not exactly once.

A stable delivery key can be:

```text
<hook-id>:<event-id>
```

If a hook launches a Flow, its initial invocation key can derive from that pair. Jig can then avoid starting two identical invocations after a restart when the first has already completed.

Hook code should still be reasonably idempotent.

## Preventing event loops

The architecture makes loops easy:

```text
agent.message
    ↓
monitoring Flow runs an Agent
    ↓
agent.message
    ↓
monitoring Flow runs again
```

The core event envelope should include:

```text
causedBy
origin
depth
correlationId
```

Local hooks can filter:

```ts
if (
  event.origin?.flow ===
  "agent-message-monitor"
) {
  return;
}
```

Jig should also impose a configurable maximum causal depth. It should not try to guess every logical recursion pattern.

## Concurrency rules

A hook should not silently introduce concurrent writers into the same project worktree.

A safe default is:

```text
Hook-triggered Flow on an active Task
    queued behind the active mutating invocation
```

For real-time monitoring, the local hook may deliberately request an observational invocation that:

- receives a read-only project view;
- writes only to a dedicated task artifact namespace;
- or uses an isolated worktree.

That policy should be explicit. The default must not allow two unrelated hook-triggered Flows to modify the same checkout concurrently.

## What belongs in Jig core

The non-replaceable kernel is small:

```text
Event journal
Event subscriptions and delivery tracking
Task registry
Flow scheduler
FLOW protocol host
Caskada execution
Locks and cancellation
Dynamic FLOW.md catalogue
```

This is infrastructure, not policy.

## What belongs in the Starter

Everything opinionated remains editable:

```text

Triage trigger
Kanban transitions
Agent monitoring

Git worktree lifecycle
Git commit policy

```

A Starter may provide good defaults, but none are privileged.

This distinction matters:

> **Ultimate customization does not mean eliminating the kernel. It means keeping policy out of the kernel.**

## No `HOOK.md` standard in version one

Hooks are project-specific bindings between local events and Flows. Their usefulness often depends on:

- the project directory structure;
- local Agent roles;
- chosen Kanban states;
- notification systems;
- worktree policy;
- desired monitoring frequency.

They do not need a second portable ecosystem standard yet.

Portable behavior belongs in `FLOW.md`.

Local policy belongs in hook code.

When sharing a complete opinionated set of hooks, use a Starter. When sharing reusable behavior used by a hook, publish it as a Flow.

## Recommended v1 model

The complete model becomes:

```text
Task
    Durable unit of work.

Node
    One executable graph operation.

Flow
    Composition of Nodes and Flows.

Router
    Selects the next Node or Flow.

Event
    Immutable fact emitted by the runtime or local integration.

Hook
    Ordinary project code subscribing to an Event and optionally
    scheduling a Flow.
```

Only the first four are orchestration primitives. Event delivery is runtime infrastructure. Hook is a project-level coding pattern.

The governing rules should be:

1. **There is no privileged entry Flow.**
2. **Any event source may initiate work.**
3. **Hooks are local event-to-Flow bindings, not graph primitives.**
4. **Complex hook behavior belongs in reusable Flows.**
5. **Hooks observe; Flows control.**
6. **Hooks fan out; Flows sequence.**
7. **Events are durable and delivered at least once.**
8. **Task-scoped events trigger Flows with the same Task and the event as context.**
9. **Specific hooks and sources are copied from Starters and fully editable.**
10. **The kernel supplies reliability but no workflow policy.**

This makes inbox-driven project building only one installation pattern for Jig rather than the definition of Jig itself.

Trying to make every coding agent expose exactly the same detailed event stream would force Jig toward the lowest common denominator. Instead, use three layers.

```text

agent.input.submitted
agent.completed
agent.failed
agent.cancelled
```

Jig knows when it starts the process, sends the task, receives the final result, encounters an error, or cancels the session.

These events are universally safe for generic hooks.

```ts

  async event => {
    await jig.flows.start({
      taskId: event.taskId,
      trigger: event,
      selector: {
        intent:
          "Review the work completed by the coding agent",

  },
  {
    id: "review-completed-agent-work",
  },
);
```

### 2. Optional normalized events

A capable Agent integration may additionally emit:

```text
agent.turn.started
agent.turn.completed

agent.output.delta
agent.output.completed

agent.tool.started
agent.tool.completed

agent.files.changed
agent.plan.updated

agent.approval.requested
agent.approval.resolved
```

## The local `Agent` contract

The base `Agent` can own guaranteed lifecycle behavior while allowing the local implementation to report richer events:

```ts
abstract class Agent extends Node {
  protected abstract execute(
    context: AgentContext,
  ): Promise<AgentResult>;

  async run(
    context: AgentContext,
  ): Promise<AgentResult> {
    await context.events.emit(
      "agent.started",
      {
        provider: this.provider,
        role: this.role,
      },
    );

    try {
      await context.events.emit(
        "agent.input.submitted",
        {
          provider: this.provider,
          role: this.role,
        },
      );

      const result = await this.execute(context);

      await context.events.emit(
        "agent.completed",
        {
          provider: this.provider,
          role: this.role,
          result,
        },
      );

      return result;
    } catch (error) {
      await context.events.emit(
        "agent.failed",
        {
          provider: this.provider,
          role: this.role,
          error: serializeError(error),
        },
      );

      throw error;
    }
  }
}
```

The context exposes separate methods for normalized and raw events:

```ts
interface AgentContext {
  task: Task;
  session: AgentSession;
  signal: AbortSignal;

  events: {
    emit(
      type: AgentEventType,
      data: unknown,
    ): Promise<void>;

    emitProvider(
      namespace: string,
      type: string,
      data: unknown,
    ): Promise<void>;
  };
}
```

A conceptual Codex implementation:

```ts
class Codex extends Agent {
  readonly provider = "codex";

  protected async execute(
    context: AgentContext,
  ): Promise<AgentResult> {
    const client = await startCodexAppServer({
      cwd: context.task.cwd,
      sessionRoot: context.session.root,
      signal: context.signal,
    });

    const turn = await client.startTurn(
      await this.buildPrompt(context),
    );

    for await (const notification of turn.events) {
      await context.events.emitProvider(
        "codex",
        notification.method,
        notification.params,
      );

      for (
        const event
        of normalizeCodexEvent(notification)
      ) {
        await context.events.emit(
          event.type,
          event.data,
        );
      }
    }

    return turn.result();
  }
}
```

This is where Codex event handling belongs.

## Four possible Codex observation modes

The local component can support several modes without changing hooks.

### Managed App Server mode

```text
Jig starts Codex App Server
Jig controls the thread and turn
Jig receives the complete event stream
```

This should be the recommended default. OpenAI describes App Server as the first-class integration method for exposing the complete Codex harness through a stable, bidirectional event stream.  ([Unlocking the Codex harness: how we built the App Server | OpenAI](https://openai.com/index/unlocking-the-codex-harness/))

### Managed `codex exec --json` mode

```text
Jig starts one Codex execution
Jig reads JSONL from stdout
Execution ends with the process
```

This is simpler and appropriate for self-contained Agent nodes, while still providing structured events.  ([Non-interactive mode | ChatGPT Learn](https://developers.openai.com/codex/non-interactive-mode))

### Attached mode using native Codex hooks

For sessions not directly controlled through App Server, the local Codex component can install Codex-native hooks that forward lifecycle facts to a Jig event-ingress socket or command.

Codex currently exposes hooks around session start/end, user prompt submission, tool use, permissions, compaction, subagents, and stopping.  ([Hooks | ChatGPT Learn](https://developers.openai.com/codex/hooks))

Those provider hook files still belong here:

```text
agents/codex/provider-hooks/
```

They are part of the Codex implementation—not Jig project hooks.

### File-watcher fallback

Watching Codex transcripts or event files should be the final fallback for an external session that provides no supported live interface.

This mode is inherently weaker:

- events may arrive late;
- partial writes need handling;
- rotations and renames need handling;
- process crashes may leave incomplete records;
- provider formats can change;
- intent such as “this turn is now waiting” may be difficult to infer.

Codex’s own documentation explicitly says its transcript path is provided for convenience and that the transcript format is not a stable hook interface.  ([Hooks | ChatGPT Learn](https://developers.openai.com/codex/hooks))

Therefore:

```text
App Server stream     preferred
exec --json stream    simple managed alternative
native Codex hooks    attached-session alternative
transcript watcher    last-resort compatibility mode
```

All four remain internal strategies of the same `Codex` component.

Yes. Flows should be able to observe and wait for events, but that must not blur three different mechanisms:

| Mechanism | Purpose | Control semantics |
|---|---|---|
| **Hook** | React independently to a fact | Starts detached work; the producer does not wait |
| **Flow call** | Ask another Flow to perform work | Parent waits for the child result |
| **Event wait** | Wait for an external fact to occur | Current node pauses until a matching event arrives |

The governing rule should be:

> **Use `flow.call` for work, `events.wait` for facts, and hooks for independent reactions.**

That distinction prevents hidden flow composition through hooks.

# 1. Flows should have `events.query` and `events.wait`

A Flow may need to wait for:

```text
agent.output.completed
human.approval.granted
git.merge.completed
artifact.uploaded
external.build.completed
input.file.created
```

That should be a normal host effect:

```ts
const result = await effects.request(
  "events.wait",
  {
    taskId: task.id,

    types: [
      "agent.output.completed",
    ],

    after: agentStartedEvent.id,

    scope: {
      agentInvocationId,
    },

    timeoutMs: 120_000,
  },
);
```

The node’s `exec()` awaits that response. The Caskada graph remains alive and resumes normally after the event arrives.

## Required semantics

`events.wait` should:

1. Search the durable event journal first.
2. If no matching event exists, atomically register a waiter.
3. Return the complete matching event.
4. Never consume or remove the event.
5. Support cancellation.
6. Treat timeout as a normal result, not a protocol failure.
7. Use explicit scope and cursor fields rather than connection state.

The cursor is important:

```text
after: E-00942
```

Without it, this race is possible:

```text
Flow checks for event
    ↓
Event is emitted
    ↓
Flow begins listening
    ↓
Event has been missed
```

The host must perform “query after cursor, otherwise subscribe” as one logical operation.

## Keep matching deliberately small

Version one should support only deterministic fields such as:

```text
event type
task ID
invocation ID
agent invocation ID
correlation ID
origin
after cursor
```

It should not introduce a JSON expression language:

```yaml
where:
  and:
    - equals: ...
    - contains: ...
```

The Flow can inspect returned event data in code and continue waiting if necessary.

## Events are not consumed

The same event may be relevant to:

```text
a waiting Flow
a monitoring hook
a checkpoint hook
a user interface
an audit logger
```

Therefore, event handling must be non-destructive.

Consumer progress is tracked separately:

```text
Hook delivery:
    <hook-id, event-id>

Flow wait:
    stored in Flow memory or task state

Dashboard:
    its own cursor
```

---

# 2. Long waits should remain hook-driven

An active Flow may wait for a bounded period:

```text
seconds
minutes
possibly the lifetime of an active agent session
```

It should not ordinarily remain alive for:

```text
three days awaiting human approval
a week awaiting a GitHub response
an indefinite external trigger
```

The distinction should be:

```text
Short, invocation-scoped wait
    events.wait

Long, durable wait
    Flow finishes with waiting/blocked
    Hook later starts a new invocation
```

For example:

```text
Review Flow
    ↓
publishes approval request
    ↓
returns outcome: waiting-for-approval
    ↓
process exits
```

Later:

```text
human.approval.granted
    ↓
local hook
    ↓
starts approval-follow-up Flow
```

This avoids pretending that Jig can persist and restore an arbitrary Caskada call stack.

The restarted Flow receives:

```text
the same Task
the triggering approval event
the persisted task artifacts
```

It can determine what remains to be done from durable task state.

## A Flow should not rely on a hook to continue its own graph

This would be fragile:

```text
Flow emits research.requested
    ↓
project hook notices it
    ↓
hook starts Research Flow
    ↓
Research Flow emits research.completed
    ↓
original Flow waits for research.completed
```

That hides required control flow inside project hooks and can deadlock under task locks or scheduler limits.

Use:

```text
flow.call("research")
```

instead.

Hooks should remain detached policy:

```text
notify
monitor
checkpoint
synchronize external systems
start unrelated follow-up work
```

# 3. Introduce one contract model: `requires` and `provides`

The increasing number of events, profiles, flows, host effects, and outcomes does need a coherent declaration system.

It should apply only to **cross-component boundaries**.

Do not declare every Caskada action.

```text
Internal Caskada action
    private implementation detail

Root Flow outcome
    public interface

Event sent to Jig
    public interface

Agent role requested
    public dependency

Host effect requested
    public dependency

Child Flow capability requested
    public dependency
```

A possible `FLOW.md` contract is:

```markdown
---
name: gauntlet-loop

description: >
  Builds or materially improves an artifact through repeated
  implementation, evaluation, criticism, and revision.

outcomes:
  done: The requested quality bar has been reached.
  blocked: Progress cannot continue without external input.

requires:
  capabilities:
    - agent.run
    - flow.call
    - events.wait

  agents:
    builder: Build or improve the artifact.
    reviewer: Independently evaluate the result.

  flows:
    research: >
      Research and justify an appropriate comparison target
      when none has been established.

  events:
    - human.approval.granted

provides:
  events:
    - gauntlet.iteration.completed
    - gauntlet.quality-bar.reached
---
```

This is static interface metadata, not executable routing logic.

It contains no:

```text
conditions
mappers
loops
branches
path expressions
state transformations
```

All behavior remains in code.

## Logical Flow requirements remain semantically resolved

This declaration:

```yaml
flows:
  research: >
    Research and justify an appropriate comparison target.
```

does not point at:

```text
./flows/deep-research
github:user/research
research@2.0
```

It defines a logical requirement and its semantic meaning.

When the native implementation requests the `research` slot, Jig can:

1. Inspect installed `FLOW.md` files.
2. Retrieve likely candidates.
3. Use the SemanticRouter.
4. Select a compatible Flow.
5. Run it through `flow.call`.

A project can still explicitly bind the slot when deterministic behavior is desired:

```ts
flows: {
  research: "./flows/company-research",
}
```

Dynamic discovery remains the default.

# 4. Do not create a central authored registry

The contract catalogue should be **derived from local declarations**, not manually maintained in one large file.

Different components expose their surface differently.

## Flows

Portable requirements and provisions live in `FLOW.md`.

The Jig/Caskada implementation can additionally be inspected to verify that the code matches the declaration.

## Agent profiles

A project binding provides an Agent role:

```text
agent/builder
agent/reviewer
```

The concrete Agent component declares the events and features it guarantees:

```text
agent.started
agent.completed
agent.failed
agent.output.completed
agent.tool.started
agent.files.changed
```

A configured profile may expose fewer events than the underlying provider supports. The effective configured profile is what matters.

## Hooks

Hook registration already declares consumption:

```ts
jig.events.on(
  "agent.completed",
  handler,
  {
    id: "checkpoint-after-agent",
  },
);
```

There should be no separate `HOOK.md` or hook dependency manifest.

## Event sources

An event-producing integration declares what it emits alongside its implementation.

For example, the local Codex component may declare:

```text
guaranteed:
    agent.started
    agent.completed
    agent.failed

available in app-server mode:
    agent.output.delta
    agent.tool.started
    agent.files.changed
```

## Host

The host provides effects such as:

```text
agent.run
flow.call
events.query
events.wait
event.emit
```

## Generated catalogue

Jig then produces one derived contract graph:

```text
Flow requirements
Agent bindings
Agent event capabilities
Hook subscriptions
Event producers
Host capabilities
Flow outcomes
```

This can be cached internally, but the cache is never the authored source of truth.

# 5. Checks can become substantially more powerful

Once everything exposes `requires` and `provides`, `jig check` can reason about the whole project rather than merely validating files.

## Capability checks

```text
gauntlet-loop requires agent/builder
    → provided by agents/codex-builder

gauntlet-loop requires agent/reviewer
    → provided by agents/claude-reviewer

gauntlet-loop requires events.wait
    → provided by Jig host
```

## Event compatibility

Suppose a Flow waits for:

```text
agent.output.completed
```

but the selected Agent profile only guarantees:

```text
agent.started
agent.completed
agent.failed
```

Jig can reject this before execution:

```text
Error: unsatisfied event dependency

Flow:
  gauntlet-loop

Waits for:
  agent.output.completed

Agent profile:
  legacy-builder

The profile does not provide this event.
```

This directly addresses the provider-granularity issue discussed with Codex.

## Dead-wait detection

```text
Flow waits for human.approval.granted
No event source provides human.approval.granted
```

Possible result:

```text
Error
```

Or, when declared external:

```text
Warning: external producer not verifiable
```

## Hidden hook dependency detection

```text
Flow waits for research.completed
Only producer is a hook-triggered Research Flow
```

Jig can warn:

```text
The Flow appears to depend on a detached hook reaction.

Use flow.call for required work.
```

## Causal-loop detection

```text
agent.completed
    → hook starts monitor Flow

monitor Flow runs Agent
    → agent.completed

agent.completed
    → hook starts monitor Flow
```

Jig can identify the potential loop using:

```text
hook consumes event
Flow provides event
hook starts Flow
```

## Impossible ordering

```text
Flow waits for build.completed
The only reachable producer occurs after the waiting node
```

For native Caskada Flows, graph inspection may detect that liveness failure.

## Semantic Flow resolution

For a declared requirement such as:

```text
research:
    Find and justify a comparison target
```

Jig can report:

```text
Strong candidate:
    deep-comparative-research       0.91

Other candidates:
    web-research                    0.72
    repository-research             0.54
```

Strict mode can require:

```text
one explicit binding
or
one candidate above a configured confidence threshold
or
an internal fallback
```

## Contract drift

Jig can compare authored declarations with runtime observation:

```text
Undeclared event emitted:
    gauntlet.review.failed

Declared event never observed:
    gauntlet.iteration.completed

Undeclared host effect requested:
    human.request
```

“Never observed” should normally be informational because not every branch executes. An undeclared requirement can be a strict-mode error.

## Useful commands

```bash
jig check

jig graph --contracts

```

The contract graph can become one of Jig’s strongest features.

# 6. MCP’s statelessness lesson applies directly

Older MCP revisions required an initialization handshake that established protocol version, capabilities, and implementation information for the session. The July 28, 2026 specification removed protocol-level sessions and initialization from the modern protocol: each request now carries its protocol version, capabilities, and relevant identity metadata, while `server/discover` is available as an optional discovery operation. State that spans requests is represented through explicit handles rather than inferred from a connection.  ([Lifecycle](https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle?utm_source=chatgpt.com))

The current MCP specification is explicit that a connection or process is not a conversation or session. Related requests can be interleaved, and any state spanning requests must be referenced by an explicit identifier. Even long-lived notification streams are scoped to an individual request rather than to the underlying connection.  ([Overview](https://modelcontextprotocol.io/specification/2026-07-28/basic?utm_source=chatgpt.com))

That is the correct lesson for FLOW/1:

> **Do not make the connection, process, or initialization handshake the owner of semantic state.**

## Remove mandatory initialization from FLOW/1

The earlier proposal included:

```text
flow/initialize
    ↓
flow/run
```

I would now remove the mandatory initialization phase.

Every request should carry its own metadata:

```json
{
  "jsonrpc": "2.0",
  "id": "E-0017",
  "method": "events/wait",
  "params": {
    "_meta": {
      "protocolVersion": "1",
      "caller": {
        "name": "gauntlet-loop",
        "version": "1.2.0"
      },
      "capabilities": {
        "cancellation": true
      },
      "taskId": "T-0042",
      "invocationId": "I-0011",
      "effectId": "I-0011:review-wait",
      "attempt": 1
    },
    "types": [
      "agent.output.completed"
    ],
    "after": "E-0917",
    "timeoutMs": 120000
  }
}
```

The receiver can process that request without knowing what happened earlier on the connection.

## Discovery should be optional

FLOW/1 may expose something such as:

```text
host/discover
flow/describe
```

for:

```text
editors
jig check
UI hydration
compatibility display
```

But a caller should be allowed to optimistically invoke a capability and receive a structured unsupported-capability error.

MCP’s current protocol similarly permits clients to call operations directly and handle a version or capability failure, while discovery remains available when up-front information is useful.  ([Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover?utm_source=chatgpt.com))

# 7. Distinguish protocol state, durable state, and execution state

“Stateless” must not mean “the system stores nothing.”

Jig necessarily has state. The goal is to make it explicit and correctly owned.

| State | Owner | Storage |
|---|---|---|
| Task data | Task capsule | Durable files |
| Event history | Event journal | Durable append-only store |
| Hook delivery cursor | Hook delivery store | Durable |
| Effect results | Effect journal | Durable, keyed by effect ID |
| Agent session | Agent integration | Explicit `agentSessionId` |
| Active Caskada memory | Flow process | Ephemeral |
| Pending JSON-RPC correlation | Transport handler | Ephemeral |
| Connection identity | Nobody | Must not carry semantic meaning |

The architecture becomes:

```text
Stateless control plane
    Handles self-contained requests.

Durable data plane
    Task files, event journal, effect journal, leases.

Stateful invocation worker
    Owns one live graph continuation.
```

This is the realistic boundary.

## The Flow runtime remains stateful while running

A Caskada invocation has:

```text
current graph position
memory
branch state
retry state
pending nodes
call stack
```

Making that fully stateless would require:

```text
checkpointing
serialized continuations
deterministic replay
effect replay
stable node identities
```

That is not a version-one feature.

If the Flow process crashes while awaiting an event or Agent result, the invocation fails. Jig may retry the entire invocation according to project policy, but it should not claim transparent continuation.

## The host can still be restart-friendly

Durable information remains available:

```text
the event is still in the journal
completed effects remain recorded
task artifacts remain present
hook delivery positions remain stored
```

A retried Flow can query what already happened.

That is valuable even without full continuation recovery.

---

# 8. Every effect needs an explicit identity

To support retries without duplicating work, distinguish:

```text
JSON-RPC request ID
    Transport correlation.

effectId
    Semantic operation identity.

attempt
    Intentional retry number.
```

For example:

```text
effectId:
    I-0011:builder-agent

attempt:
    2
```

The host can apply:

```text
same effectId + same attempt
    Return previously recorded result.

same effectId + higher attempt
    Perform an intentional retry.

new request ID
    Has no bearing on semantic identity.
```

This matters for:

```text
agent runs
child Flow calls
Git commits
human approval requests
event waits
```

It also makes stateless workers possible: a new worker can consult the durable effect journal rather than relying on an in-memory session.

---

# 9. Do not copy every part of MCP’s stateless design blindly

MCP’s July 2026 revision also replaced server-initiated requests with a multi-round-trip pattern in which a result can request additional input and the original operation is retried with those responses.  ([Key Changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog?utm_source=chatgpt.com))

That approach is less suitable for Jig’s active graph runtime in version one.

Forcing this:

```text
Caskada reaches Agent node
    ↓
returns input_required
    ↓
process exits
    ↓
Jig runs Agent
    ↓
restarts Flow from beginning with response
```

would require deterministic graph replay or serializable checkpoints.

Instead, keep the current hosted-effect model:

```text
Caskada node sends agent.run
    ↓
node awaits response
    ↓
Jig runs Agent
    ↓
response resolves Promise
    ↓
Caskada continues
```

The request remains self-contained and invocation-scoped, even though the parent process remains alive.

The correct lesson from MCP is not:

> Never keep a request open.

It is:

> Never let an implicit connection session carry information that should be explicit in a request or handle.

# 10. Recommended FLOW/Jig v1 decisions

I would put the following into version one.

## Event access

```text
events.query
    Read matching durable events.

events.wait
    Wait for one matching event with cursor, scope, timeout,
    and cancellation.
```

No streaming event API is required initially.

## Hook rule

```text
Hooks react independently.
Flows never depend on hook completion for required progress.
```

## Flow composition

```text
flow.call
    Required child work.

events.wait
    Required external fact.

handoff
    Transfer responsibility and terminate current invocation.
```

## Contract surface

FLOW.md may declare:

```text
required host capabilities
required Agent roles
logical child Flow requirements
required event types
provided event types
public outcomes
```

No private Caskada actions.

## Derived project graph

Jig combines:

```text
FLOW.md contracts
Caskada graph inspection
Agent profile capabilities
hook registrations
event-source declarations
host capabilities
```

No manually maintained central registry.

## Stateless protocol rules

```text
No mandatory initialization handshake.
Every request carries protocol version and capabilities.
Every stateful concept has an explicit ID.
Connection identity has no semantic meaning.
Discovery is optional.
Long-lived waits are request-scoped.
```

## Explicit limitation

```text
Active Flow continuation is not crash-durable in v1.
```

## Higher checks

At minimum:

```text
missing Agent role
missing host capability
event wait with no producer
Flow requirement with no candidate
hook-trigger cycle
impossible wait ordering
unsupported Agent event granularity
undeclared public outcome
undeclared external effect
duplicate semantic effect
scheduler deadlock risk
```

The refined architecture is:

```text
Flow
    owns control.

Host
    owns effects.

Event journal
    owns facts.

Hook
    reacts independently.

Contract graph
    proves that the pieces can work together.

Explicit handles
    carry state across requests.
```

That keeps Jig highly customizable while giving it much stronger correctness checks and a protocol that does not repeat MCP’s original reliance on connection-scoped initialization and session state.
