# Final architecture

The strongest design is a **three-layer system with a deliberately thin boundary**:

```text
FLOW
    Open package and interoperability standard

Jig
    File-native host, lifecycle kernel, resolver, scheduler and reconciler

Caskada v3
    Jig’s native graph runner
```

Cordis, plain Python, LangGraph, Mastra, compiled binaries, and future runtimes participate through FLOW without becoming Jig dependencies.

The governing rule is:

> **Runners own control. Jig owns environment and lifecycle. FLOW owns the boundary.**

This architecture is portable without making Jig runtime-neutral, extensible without reproducing Cordis over RPC, and dynamic without turning every operation into an LLM decision.

# 1. The non-negotiable invariants

These decisions should be treated as architectural law.

## 1. Internal control belongs to the runner

Caskada owns:

```text
nodes
edges
loops
branches
retries
internal subflows
graph state
next-node selection
```

Cordis owns:

```text
plugins
fibers
local services
reactive activation
local events
local effect cleanup
```

Jig never mirrors either runtime’s internal model.

## 2. External operations belong to the host

Jig owns:

```text
Flow discovery
Flow selection
Agent providers
Agent sessions
Spaces
event persistence
capability binding
permissions
cancellation
processes
durable history
```

A runner requests these operations and waits for their results.

## 3. Simple Flows require no formal contract

A Flow that:

```text
runs Agents
reads and writes files
calls another Flow
emits events
returns an outcome
```

does not need a capability contract.

It should work from `FLOW.md`, optional executable code, and the generic FLOW invocation protocol.

## 4. Flows compose by intent; services compose by contract

Use a Flow call for:

```text
Research this subject.
Review this result.
Generate a plan.
Repair this implementation.
```

Use a capability contract for:

```text
Open and maintain a session.
Register a UI contribution.
Read and subscribe to a session store.
Expose a command registry.
Provide several callable operations over a stable lifetime.
```

This is the most important conceptual distinction:

> **A Flow performs work. A capability provides an interface.**

## 5. A Scope owns every runtime resource

Listeners, processes, sessions, registrations, temporary files, child Flows, and capability providers must have an explicit owner.

When the Scope closes, host-owned resources are released deterministically.

## 6. Connections carry messages, not identity

A socket or process connection is not a session, component, Scope, or Run.

Stateful concepts have explicit handles:

```text
scopeId
runId
mountId
bindingId
providerId
agentSessionId
effectId
```

Current MCP work reflects the same architectural lesson: the protocol can remain stateless while application state is represented by explicit handles and per-request metadata.  ([https://modelcontextprotocol.io/seps/2567-sessionless-mcp](https://modelcontextprotocol.io/seps/2567-sessionless-mcp))

## 7. Bind once, use repeatedly

Semantic routing happens when a dependency is first bound, not on every use.

A bound provider is pinned for the Scope.

## 8. Events are facts

Events cannot secretly become middleware or execution gates.

```text
Hooks react.
Flows sequence.
Capability policies intercept effects.
```

## 9. Files describe desired state

Jig continuously reconciles the files users own with the runtime state it manages.

The filesystem is authoritative; the active runtime is derived.

## 10. Dynamic choices must be visible

Every selected Flow, provider, revision, patch set, Agent profile, and capability binding is journaled.

There is no invisible LLM-driven mutation of architecture.

# 2. The complete layer model

```text
Sources and indexes
        ↓
Installer + provenance + patches
        ↓
Desired project file tree
        ↓
Jig reconciler
        ↓
FLOW catalogue + provider catalogue
        ↓
Binding resolver
        ↓
Scheduler
        ↓
Caskada / Cordis / external FLOW runner
        ↕ FLOW/1
Jig effects, capabilities, Agents, Spaces and events
        ↓
Durable journals and project history
```

Each layer has one responsibility.

| Layer | Responsibility |
|---|---|
| **FLOW package** | Portable meaning, instructions, resources and optional executable |
| **FLOW/1** | Invocation, scoped effects, capability calls, events and outcomes |
| **Jig** | Discovery, binding, scheduling, lifecycle, reconciliation and durability |
| **Caskada v3** | Native graph execution |
| **Cordis adapter** | Map a Cordis realm onto FLOW scopes and capabilities |
| **Starter** | User-owned application policy |
| **Capability contract** | Optional machine-verifiable API for structured services |

# 3. FLOW is a package standard

The portable artifact is a directory:

```text
gauntlet-loop/
├── FLOW.md
├── flow.ts              # optional
├── prompts/
├── skills/
├── references/
├── scripts/
├── assets/
└── contracts/
```

Only `FLOW.md` is required.

This follows the successful progressive-disclosure pattern of Agent Skills: one predictable Markdown entrypoint, minimal metadata, and optional bundled resources. Agent Skills require only `name` and `description` in `SKILL.md`; scripts, references, and assets remain ordinary files.  ([https://agentskills.io/specification](https://agentskills.io/specification))

## `FLOW.md` is normative

A basic Flow:

```markdown
---
name: gauntlet-loop
description: >
  Builds or materially improves an inspectable artifact through
  repeated implementation, evaluation and revision.
---

# Gauntlet Loop

Inspect the current Space and determine whether an adequate quality
target exists.

When no suitable target exists, call a Flow that can research and
justify one.

Build the artifact, test it, obtain an independent review, and repeat
while material deficiencies remain.

Complete only when the available evidence supports the requested
quality level.
```

This Flow is valid without code.

An agentic host can invoke it through a conductor Agent.

## Optional public outcomes

```markdown
---
name: gauntlet-loop
description: >
  Builds or materially improves an inspectable artifact.

outcomes:
  done: The requested quality level has been reached.
  blocked: Progress cannot continue without external input.
---
```

Custom outcomes are optional. `done`, failure, cancellation, and protocol errors remain distinguishable.

## Optional executable

A Flow may include exactly one conventional executable:

```text
flow
flow.ts
flow.js
flow.py
flow.sh
```

The executable speaks FLOW/1.

There are no profile filenames such as:

```text
flow.jig.ts
flow.cordis.ts
flow.langgraph.py
```

The internal framework is private.

A `flow.ts` may internally use:

```text
Caskada
Cordis
plain TypeScript
another framework
```

The host only cares that the launched program conforms to FLOW/1.

## Execution selection

```text
Supported executable exists
    → execute it

No executable exists
Unsupported local runtime
Explicit interpreted mode
    → interpret FLOW.md using the host conductor
```

This gives every package a universal semantic fallback while allowing deterministic native implementations.

## FLOW is not formally a superset of SKILL

They share a packaging philosophy, but have different semantics.

| Skill | Flow |
|---|---|
| Loaded into an Agent | Invoked or mounted by a host |
| Teaches a capability | Coordinates work or provides a component |
| Passive instructions | Owns a runtime Scope |
| No public completion result | Returns an outcome |
| No independent lifecycle | May own child resources |
| Usually one Agent context | May coordinate Agents, Flows and capabilities |

# 4. FLOW/1 is a scoped-capability ABI

FLOW/1 should use JSON-RPC 2.0 rather than inventing another request envelope. JSON-RPC already defines bidirectional requests, correlated responses, notifications and standard errors.  ([https://www.jsonrpc.org/specification](https://www.jsonrpc.org/specification))

The required local transport is stdio:

```text
stdout
    protocol messages only

stderr
    logs and diagnostics
```

Other transports may be defined later without changing the method semantics.

## The protocol vocabulary

FLOW/1 needs only these operations.

### Host to component

| Method | Purpose |
|---|---|
| `flow/run` | Invoke a Flow and await one final result |
| `flow/mount` | Activate a long-lived component and return a mount handle |
| `scope/cancel` | Cancel and close a Run or mounted Scope |
| `capability/invoke` | Invoke a capability provided by the component |

### Component to host

| Method | Purpose |
|---|---|
| `flow/call` | Invoke another Flow and await its result |
| `capability/call` | Invoke one of the component’s bound capabilities |
| `capability/provide` | Register a capability owned by the current Scope |
| `event/emit` | Publish an observational event |

That is the entire universal control surface.

Agent sessions, event queries, UI registration, filesystems, human approvals, Git, databases, and notifications are capability APIs built over this surface.

## Per-request metadata

Every request carries:

```json
{
  "_meta": {
    "protocolVersion": "1",
    "scopeId": "S-104",
    "runId": "R-42",
    "effectId": "R-42/build/agent/1",
    "attempt": 1,
    "correlationId": "C-18"
  }
}
```

No mandatory initialization session is required.

Discovery may exist, but request validity must not depend on connection history.

## `flow/run`

```json
{
  "jsonrpc": "2.0",
  "id": "RUN-42",
  "method": "flow/run",
  "params": {
    "_meta": {
      "protocolVersion": "1",
      "scopeId": "S-104",
      "runId": "R-42"
    },
    "space": {
      "id": "SPACE-17",
      "uri": "jig-space:R-42",
      "path": "/project/.jig/spaces/runs/R-42"
    },
    "input": {},
    "trigger": {
      "type": "input.file.created",
      "eventId": "E-91"
    },
    "bindings": {}
  }
}
```

The request remains pending while the Flow runs.

Completion:

```json
{
  "jsonrpc": "2.0",
  "id": "RUN-42",
  "result": {
    "outcome": "done",
    "output": {
      "artifact": "artifacts/review.md"
    }
  }
}
```

## `flow/call`

Generic Flow composition remains intent-driven:

```json
{
  "jsonrpc": "2.0",
  "id": "CALL-11",
  "method": "flow/call",
  "params": {
    "_meta": {
      "protocolVersion": "1",
      "scopeId": "S-104",
      "runId": "R-42",
      "effectId": "R-42/research/1"
    },
    "slot": "comparison-research",
    "selector": {
      "intent": "Research and justify a suitable comparison target"
    },
    "input": {
      "subject": "football game quality benchmark"
    }
  }
}
```

Jig:

1. Retrieves candidate `FLOW.md` packages.
2. Applies deterministic eligibility rules.
3. Uses the SemanticRouter when more than one valid candidate remains.
4. Pins the selected package for the parent Scope.
5. Creates a child Scope.
6. Runs the selected Flow.
7. Returns the child outcome.
8. Resumes the parent.

The runner process never gives Jig control over its internal graph.

## Handoff

A handoff is a terminal Run result:

```json
{
  "outcome": "handoff",
  "selector": {
    "intent": "Build and iteratively improve the requested artifact"
  }
}
```

The current Run ends. Jig starts a new Run.

## `flow/mount`

A FLOW package declaring provided capabilities may be mounted as a long-lived component.

The mount:

```text
receives a Scope
registers capabilities
returns ready
remains available
handles capability/invoke
is disposed through scope/cancel
```

Existing bindings remain pinned to the mounted provider revision until their Scopes end.

## Idempotency

JSON-RPC request IDs correlate transport messages.

They do not identify semantic operations.

FLOW/1 therefore distinguishes:

```text
request ID
    one transport exchange

effectId
    one semantic operation

attempt
    intentional retry number
```

The host records effect results:

```text
same effectId + same attempt
    return recorded result

same effectId + higher attempt
    intentional retry

different effectId
    new operation
```

## No graph mirroring

Jig records only:

```text
Run tree
Scope tree
pending effects
selected bindings
events
outcomes
```

It does not record or control:

```text
current Caskada node
Cordis fiber stack
graph edges
branch-local runtime state
retry internals
```

# 5. Capability contracts are optional and rare

A capability contract is appropriate only when generic Flow invocation is insufficient.

Use one when a consumer needs a stable service with:

```text
multiple operations
long-lived state
subscriptions
callbacks
repeated calls
host-to-provider invocation
strict structured compatibility
```

Do not use one merely because a Flow is complicated.

## Do not invent a new interface-description language

Capability contracts should be OpenRPC documents.

OpenRPC already provides a language-neutral description format for JSON-RPC methods, parameters, results, errors and JSON Schema-based values.  ([https://spec.open-rpc.org/](https://spec.open-rpc.org/))

Example:

```json
{
  "openrpc": "1.4.0",

  "info": {
    "title": "Session Store",
    "version": "1.2.0"
  },

  "x-flow-contract": "https://example.org/contracts/session-store",

  "methods": [
    {
      "name": "list",
      "params": [],
      "result": {
        "name": "sessions",
        "schema": {
          "type": "array",
          "items": {
            "$ref": "#/components/schemas/Session"
          }
        }
      }
    },
    {
      "name": "read",
      "params": [
        {
          "name": "sessionId",
          "required": true,
          "schema": {
            "type": "string"
          }
        }
      ],
      "result": {
        "name": "session",
        "schema": {
          "$ref": "#/components/schemas/Session"
        }
      }
    }
  ]
}
```

The small FLOW-specific extension is only:

```text
x-flow-contract
    canonical contract identity
```

Contract events may use an `x-flow-events` extension or notification methods. That should be standardized only after concrete implementations prove the required shape.

## FLOW.md capability declaration

Most Flows have no capability section.

An advanced component may declare:

```markdown
---
name: session-browser
description: >
  Browses and monitors a host-provided session store.

capabilities:
  use:
    sessions:
      contract: https://example.org/contracts/session-store
      version: ^1.0

  provide:
    browser: ./contracts/session-browser.openrpc.json
---
```

The local names:

```text
sessions
browser
```

are slots.

They are not global identifiers.

## Identity separation

```text
Contract:
    https://example.org/contracts/session-store

Contract version:
    1.2.0

Provider package:
    github:alice/session-store-sqlite

Package release:
    4.7.3

Installed revision:
    sha256:82a9...

Consumer slot:
    session-browser#sessions

Binding:
    consumer slot → exact provider revision
```

Package version and capability contract version are independent.

## Version compatibility

Use Semantic Versioning for capability APIs. SemVer is meaningful only when the public API is explicitly declared, which capability contracts do.  ([https://semver.org/](https://semver.org/))

If the consumer requires:

```text
^2.0
```

and providers expose:

```text
1.8.0
3.1.0
```

there is no compatible provider.

The SemanticRouter must not select version 3 because it is newer or semantically similar.

Recovery requires:

```text
a 2.x provider
an explicit adapter
a patched consumer
a generated compatibility provider
or a pending diagnostic
```

An adapter is itself a provider:

```text
uses version 3
provides version 2
```

## Semantic routing comes after compatibility

```text
Contract
    determines whether communication is possible

SemanticRouter
    chooses the best compatible provider

Binding
    records the exact decision

Scope
    pins that decision
```

# 7. The universal runtime objects

The earlier `Task` abstraction should not be core.

The correct runtime model is:

| Concept | Responsibility |
|---|---|
| **Scope** | Lifetime and ownership |
| **Context** | Values and capability bindings visible in a Scope |
| **Space** | Managed file tree |
| **Run** | One Flow invocation |
| **Mount** | One long-lived component instance |

## Scope

A Scope owns:

```text
child Scopes
Agent sessions
event subscriptions
child processes
capability providers
temporary directories
leases
pending Flow calls
timers
```

Cleanup rules:

1. Child Scopes close before parents.
2. Scope-owned resources close in reverse registration order where ordering matters.
3. Cancellation closes the complete subtree.
4. Cleanup continues after individual disposal errors.
5. Active providers enter draining before disposal.

Cordis provides the key precedent: plugins declare service dependencies, remain pending until those services exist, and install reversible effects that are unwound during teardown.  ([https://deepseek-harness.github.io/deepseek-harness/en/reference/cordis-primer](https://deepseek-harness.github.io/deepseek-harness/en/reference/cordis-primer))

## Context

Context is the immutable view supplied to a Run or mounted component:

```text
scope identity
Space handle
resolved capability slots
configuration
trigger
event and effect access
permissions
```

It is not an ambient distributed JavaScript proxy.

Across FLOW/1, it contains serializable data and explicit handles.

## Space

Space is the generalized file capsule.

Every Jig Run and mounted component receives a private managed Space.

```text
.jig/spaces/
├── runs/
├── mounts/
└── agents/
```

A Space may contain:

```text
logs
Agent sessions
prompts
artifacts
temporary files
component-local state
provider event streams
```

Additional Spaces may be attached:

```text
source checkout
document collection
shared asset directory
database export
```

A Git worktree is one possible Space provider.

It is not a Jig requirement.

## Task

Task is an optional application-level entity.

A project-development Starter may define:

```text
Task T-0042
├── Kanban card
├── durable task Space
├── several Runs
├── Agent sessions
└── optional Git checkout Space
```

A general-purpose GUI application may have no Task concept.

# 8. Caskada v3 is Jig’s native graph runner

There should be no separate Jig Graph abstraction.

Refactor Caskada directly into v3 and make it Jig’s first-party graph engine.

FLOW remains neutral: Cordis and Caskada are equally valid FLOW runtimes.

## Preserve

```text
Node
Flow
action-labelled edges
nested Flow composition
prep → exec → post
retries
cycles
parallel branches
shared and branch-local state
```

## Replace

```text
mutable triggers
graph cloning
visit counters on Flow definitions
retry counters on Node instances
implicit merged memory proxies
runtime state stored on graph objects
```

## Caskada v3 model

```text
immutable graph definition
        ↓
compiled execution plan
        ↓
per-Run graph runner
        ↓
Node awaits host effects
        ↓
Node returns transition
        ↓
runner follows transition
```

## Node context

```ts
interface NodeContext<Shared, Local> {
  scope: {
    id: string;
  };

  run: {
    id: string;
    parentId?: string;
  };

  frame: {
    nodeId: string;
    branchId: string;
    visit: number;
    attempt: number;
  };

  state: {
    shared: Shared;
    local: Local;
  };

  space: SpaceHandle;
  effects: EffectClient;
  events: EventSink;
  signal: AbortSignal;
}
```

## Returned transitions

Instead of:

```ts
this.trigger("done");
```

use:

```ts
return transition("done");
```

Multiple branches:

```ts
return [
  transition("security-review"),
  transition("performance-review"),
];
```

## Effects

An Agent Node waits normally:

```ts
const result = await context.effects.call(
  "agent.run",
  {
    role: "builder",
    instructions: "./prompts/build.md",
  },
);
```

Caskada remains the sole graph runner.

## Inspection

A compiled graph should expose:

```text
nodes
edges
possible root outcomes
cycles
requested effects
requested Agent roles
emitted events
opaque custom nodes
```

This powers `jig check`.

FLOW does not require every runtime to expose graph topology. Caskada makes it available as a native enhancement.

## FLOW serving

Caskada v3 should include FLOW/1 serving directly:

```ts
import {
  Agent,
  Flow,
  Router,
  serve,
} from "caskada";

const flow = new Flow(...);

export default flow;

serve(flow);
```

`serve()` should activate only when the module is executed as the entrypoint. When Jig imports it as a trusted native Flow, Jig runs the same graph in-process.

No separate `@jig/caskada` translation layer is required.

## Language scope

Caskada v3 should be TypeScript-first.

Maintaining Python parity is not required for Jig’s portability because FLOW/1 is the language boundary.

A small independent Python FLOW/1 implementation should instead prove that the protocol is language-neutral.

# 9. Cordis support happens at the realm boundary

The Cordis adapter should mount one Cordis realm as one FLOW component.

It should not translate every Fiber, event or service into FLOW primitives.

## Mapping

| Cordis | FLOW/Jig |
|---|---|
| Root Context | Mounted Scope |
| Fiber | Runner-local component |
| `inject` | Required capability binding |
| Injected service | Capability proxy |
| Public provided service | `capability/provide` |
| Service method call | `capability/call` or `capability/invoke` |
| `ctx.effect()` | Scope-owned cleanup |
| Root disposal | Scope cancellation |
| Local events | Remain local unless explicitly exported |

Cordis’s Context is a service container and proxy, and dependent plugins can remain pending until required services are present.  ([https://deepseek-harness.github.io/deepseek-harness/en/reference/cordis-api/context](https://deepseek-harness.github.io/deepseek-harness/en/reference/cordis-api/context))

## Intrusiveness

The adapter touches:

```text
root Context construction
boundary service injection
boundary service publication
event translation at declared seams
root disposal
```

It does not modify:

```text
every plugin
every ctx.effect()
every event listener
the Fiber scheduler
Cordis HMR
local service resolution
```

## Important limitation

Arbitrary Cordis service objects may contain:

```text
closures
classes
symbols
non-serializable state
```

Those remain inside the Cordis realm.

Only explicitly contracted, serializable boundary services cross FLOW/1.

This is why importing a DSH plugin may require a DSH compatibility component implementing services such as sessions, commands or UI registration. Those application services belong to Jig or a compatibility package, not the FLOW core.

# 10. Agents are host-managed capabilities

Jig is agent-native, but FLOW itself remains agent-neutral.

Jig should publish an official Agent capability contract, separate from the FLOW/1 core.

## One-shot use

```text
agent.run
```

## Interactive use

```text
agent.session.open
agent.session.prompt
agent.session.cancel
agent.session.close
```

The Flow receives an explicit Agent-session handle.

It never receives the provider’s socket or SDK object.

## Agent integrations

Project-owned integrations live under:

```text
agents/
├── codex/
├── claude-code/
└── acp/
```

They own:

```text
provider startup
provider protocol
authentication
session mapping
event normalization
raw provider logs
skill projection
approvals
cancellation
```

ACP already standardizes initialization, session creation/loading, prompting, progress notifications, file and permission requests, and cancellation for coding-agent clients. It is therefore the preferred open Agent transport, while native integrations may expose additional provider-specific capabilities.  ([https://agentclientprotocol.com/protocol/v1/overview](https://agentclientprotocol.com/protocol/v1/overview))

## Events

Every Agent provides guaranteed lifecycle facts:

```text
agent.started
agent.completed
agent.failed
agent.cancelled
```

Capable integrations may additionally emit:

```text
agent.message.completed
agent.tool.started
agent.files.changed
agent.approval.requested
```

Raw native events remain namespaced:

```text
provider.codex.*
provider.claude.*
provider.acp.*
```

## Provider-specific power

A Flow needing a Codex-specific feature declares a Codex-specific capability contract.

It does not tunnel arbitrary provider JSON-RPC through FLOW/1.

# 11. Skills remain Flow-local in v1

Portable skills live with the Flow:

```text
flows/gauntlet-loop/
└── skills/
    └── testing/
        └── SKILL.md
```

The Agent integration creates a session-scoped skill projection suitable for the provider.

It must not overwrite the application’s native:

```text
.agents/skills/
.claude/skills/
```

## Customization

Imported skills are customized through Jig patches.

If a testing skill recommends Node but the project uses Bun, the patch modifies the exact Flow-local skill.

That preserves locality.

Do not introduce:

```text
implicit skill-name shadowing
global skill precedence
runtime extends folders
runtime override folders
skill dependency resolution
```

A future explicit composition mechanism may materialize one effective skill from ordered sources, but it should not be part of v1.

# 12. Events and hooks

## Event producers own observation

```text
Codex integration
    produces Codex and normalized Agent events

filesystem watcher
    produces file events

Caskada
    produces graph events

Git component
    produces repository events
```

A monitoring hook must not parse another integration’s private files.

## Durable event envelope

```ts
interface JigEvent<T> {
  id: string;
  type: string;
  at: string;

  scopeId?: string;
  runId?: string;
  providerId?: string;

  causedBy?: string;
  correlationId?: string;
  sequence: number;

  data: T;
}
```

## Hooks are local policy

A hook is ordinary code:

```ts
jig.events.on(
  "agent.completed",
  async event => {
    await jig.flows.start({
      trigger: event,
      selector: {
        intent:
          "Review the completed Agent work",
      },
    });
  },
  {
    id: "review-agent-completion",
  },
);
```

There is no Hook class and no `HOOK.md`.

## Rules

```text
Hooks fan out.
Flows sequence.
Events are non-consuming.
Delivery is at least once.
Hook deduplication uses hookId + eventId.
```

## Flow event waits

Flows may query or wait through Jig’s event capability.

Short waits are allowed.

For long human or external waits:

```text
Flow returns waiting/blocked
process exits
later event arrives
hook starts a new Run
```

Jig v1 should not claim durable restoration of an arbitrary live graph continuation.

---

# 13. Dynamic discovery and binding

There are two separate resolution systems.

## Flow selection

Used for generic work.

Input:

```text
intent
current Context
FLOW.md descriptions
eligibility
permissions
cost
quality signals
```

Output:

```text
one Flow package revision
```

Compatibility is guaranteed by generic FLOW invocation.

The SemanticRouter may make the final selection.

## Capability binding

Used for structured services.

Order:

```text
1. Reuse valid locked binding.
2. Match exact contract identity.
3. Apply version-range compatibility.
4. Apply permissions and availability.
5. Apply explicit project binding.
6. Use SemanticRouter only among remaining compatible providers.
7. Persist and pin the result.
```

## Binding lifetime

```text
Capability binding
    pinned for Scope

Generic Flow call with a slot
    cached for Scope by default

Generic Flow call without a slot
    selected per call

Explicit project binding
    reused across future Scopes until changed
```

## Missing generic Flow

Emit:

```text
flow.binding.missing
```

A Starter may react with a `create-missing-flow` Flow.

## Missing capability

Emit:

```text
capability.binding.missing
```

A repair Flow may:

```text
search indexes
install a provider
generate a provider
generate an adapter
patch the consumer
request approval
```

The incomplete environment is repaired before execution resumes.

The system must not silently invent and run an unvalidated capability provider midway through a live Run.

---

# 14. File reconciliation and hot evolution

The project tree describes desired state:

```text
jig.ts
flows/
agents/
hooks/
patches/
```

Jig reconciles that against the active runtime.

## Update sequence

```text
1. Detect file or source change.
2. Materialize a candidate revision.
3. Apply local patches.
4. Parse FLOW.md.
5. Validate contracts and bindings.
6. Inspect or compile executable code.
7. Start candidate in a shadow Scope.
8. Run conformance and health checks.
9. Publish candidate for new bindings.
10. Mark old revision draining.
11. Wait for old consumers.
12. Dispose old revision.
```

A broken edit does not destroy the running version.

```text
candidate invalid
    → retain old active revision
    → publish diagnostics
```

This is Jig’s most important Cordis-inspired improvement.

# 15. Patches are first-class Jig state

Imported source remains visibly editable:

```text
flows/gauntlet-loop/
```

Jig also retains its pristine source:

```text
.jig/sources/gauntlet-loop/<digest>/
```

Local divergence is stored as one ordered patch series:

```text
patches/
└── gauntlet-loop/
    ├── 0001-use-bun.patch
    └── 0002-remove-human-approval.patch
```

## User workflow

```text
edit normal installed files
        ↓
jig patch capture
        ↓
ordered patch recorded
```

## Update workflow

```text
new upstream
    +
local patch series
    ↓
staging materialization
    ↓
checks
    ↓
publish or repair
```

An Agent can repair patches after upstream changes.

Patches are applied during materialization.

There is no runtime overlay or hidden precedence stack.

# 16. Distribution without a mandatory registry

FLOW packages may come from:

```text
Git
npm
OCI
local directories
private indexes
public indexes
```

Package identity is:

```text
source URI

```

Capability-contract identity is an owner-controlled URI.

A public FLOW index should provide:

```text
search
metadata
descriptions

source locations
quality signals

```

It is not the source of truth and does not own the namespace.

## Installation

```bash
jig add owner/repository
jig add owner/repository --flow gauntlet-loop
jig add ./local-flow
```

A repository containing several FLOW packages is a collection, not a formal pack.

## Starters

```bash
jig init

```

A Starter is an ordinary complete Jig project copied once.

It is not a runtime dependency or package bundle.

# 18. What should be removed

The following ideas should not survive into the final design.

| Remove | Reason |
|---|---|
| **Task as a Jig primitive** | Application-specific |
| **Work as a renamed Task primitive** | Still application-specific |
| **Git worktree in core** | One optional Space provider |
| **Separate Jig Graph product** | Caskada v3 already fills that role |
| **FLOW.json** | Duplicates and bloats FLOW.md |
| **Runner profiles** | Fragment execution semantics |
| **GUI faces and slots in FLOW** | Host-specific |
| **Mandatory project graph wiring** | Regresses dynamic discovery |
| **`Flow.link()` universal API** | Source-language-specific service locator |
| **Universal graph schema** | Excludes imperative and Cordis runtimes |
| **Graph mirroring in Jig** | Creates two schedulers |
| **Capability contracts for ordinary Flow calls** | Unnecessary ceremony |
| **Custom contract language** | OpenRPC already exists |
| **Semantic routing per method call** | Slow and nondeterministic |
| **Mid-Scope provider rebinding** | Breaks consistency |
| **Implicit skill shadowing** | Violates locality |
| **Root shared-skill semantics in v1** | Adds little without explicit composition |
| **Runtime override/extend trees** | Effective state becomes hidden |
| **Mandatory central registry** | Weakens openness |
| **Raw provider-RPC tunnelling** | Bypasses policy and portability |
| **Hooks as middleware** | Hides control flow |
| **Exactly-once delivery claims** | Unrealistic |
| **Durable arbitrary graph resumption in v1** | Large unsolved runtime obligation |
| **Adapters maintained by Jig for every framework** | Unsustainable |

# 19. Architectural quality assessment

| Quality | Assessment | Limitation |
|---|---:|---|
| **Minimalism** | 8.5/10 | Advanced capability composition is necessarily non-trivial |
| **Semantic portability** | 9.5/10 | Interpretation quality depends on the host Agent |
| **Executable portability** | 9/10 | The executable’s language runtime must still be available |
| **Graph-runner fit** | 9.5/10 | Universal topology inspection is intentionally optional |
| **Cordis compatibility** | 9/10 | Application-specific services still require compatibility providers |
| **Scalability** | 8.5/10 | Live Runs are not crash-resumable in v1 |
| **Determinism** | 9/10 | Semantic Flow calls remain probabilistic before binding |
| **Extensibility** | 9.5/10 | Capability contracts and mounted providers cover deep extensions |
| **Future-proofing** | 9/10 | Requires disciplined stability of FLOW/1 |
| **User ownership** | 10/10 | Flows, Agents, hooks, patches and Starters remain source-controlled |

## What a systems architect would praise

The design has unusually strong boundaries:

- **Mechanism and policy are separated.**
- **Internal runtime semantics do not leak into the interoperability protocol.**
- **Lifetimes are explicit rather than connection-scoped.**
- **Late binding is deterministic before it becomes semantic.**
- **The filesystem is treated as desired state rather than an incidental storage location.**
- **Imported code can evolve without losing local ownership.**
- **The same component model supports one-shot work and long-lived services.**
- **The graph engine remains small because durability, Agents, discovery and installation stay outside it.**
- **The open standard does not force Jig’s implementation choices onto other hosts.**

## The main remaining risks

### FLOW.md scope creep

The frontmatter must remain small.

Whenever a proposed field expresses:

```text
branching
conditions
mapping
loops
state transformation
provider selection
```

it belongs in code or Markdown instructions, not metadata.

### Capability-contract fragmentation

Use OpenRPC, canonical owner-controlled identities, SemVer, conformance tests and contract digests.

Do not create a second bespoke interface language.

### Security

Executable Flows are arbitrary code.

Default execution should be:

```text
subprocess
private Scope
private Space
explicit capabilities
least privilege
digest-pinned source
```

Trusted native in-process execution should be opt-in or first-party only.

### Hot-reload complexity

Shadow activation and draining are more complex than immediate reload.

They are nevertheless necessary for correctness.

### Interpreted execution variance

`FLOW.md` interpretation is the universal fallback, not the highest-determinism execution mode.

Important Flows should ship executable implementations and tests.

# Final definition

## FLOW

> **FLOW is an open package and protocol standard for portable agentic procedures and scoped software components.**

It standardizes:

```text
meaning
invocation
outcomes
capability boundaries
lifetime
interoperability
```

It does not standardize:

```text
graphs
plugins
GUI
Agents
application models
package registries
internal runtime semantics
```

## Jig

> **Jig is a file-native host that discovers, binds, runs, observes, patches, and safely evolves FLOW components.**

It is opinionated about:

```text
files
Scopes
Spaces
durability
Agents
dynamic discovery
Caskada v3
user ownership
```

It is not opinionated about:

```text
Kanban
Git
worktrees
GUI
application domain
specific coding agents
specific workflows
```

## Caskada v3

> **Caskada v3 is a small effect-aware graph runner whose Flows can run natively in Jig or participate in any FLOW/1 host.**

The complete system can be summarized in one line:

> **FLOW makes components portable; Jig makes them discoverable, durable and safely evolvable; Caskada makes native graph composition elegant.**
