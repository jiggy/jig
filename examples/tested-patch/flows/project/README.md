# tested-project-patch

Supply `issue` and `editPaths`, with a read-only source attachment containing
at most 16 UTF-8 files and 64 KiB. The root invokes its exact `repair` specialist
once with captured text and package-owned CLI acceptance cases. It does not
execute candidate code or give the specialist attachments.

Validate the returned evidence against the captured files and unchanged cases.
Each valid proposal becomes an applicable patch against the original. Only a
reproduced defect and independently accepted candidate earn `review.patch`.
Failed proposals remain inspectable. Nothing applies or merges a patch.

Optional `checks` selects a reviewed `<name>-cases.json` (default `logs`).
The named file supplies 1–8 bounded, independently authored acceptance cases.

Cancellation and execution failures propagate. This example publishes final
results only; it has no batch mode or checkpoint capability.

The optional `updates` channel uses the standard user-updates contract. **Repair, Checks
and Evidence** shows the goal, independently validated checks and final deliverable
references. Jig renders these same semantic declarations in terminal and web dashboards.
Views preserve literal outcomes and explicit excerpts; they do not execute actions or
establish host success.
The separate `progress` channel retains application-owned phase records for explicit consumers; it is not the semantic dashboard channel.
