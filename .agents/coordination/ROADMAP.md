# Roadmap — capability compounding under control

Make useful methods easier to inherit and combine, and give their consumers
power under meaningful direction. This roadmap keeps outcome order and a short
view of the next steps; active plans, status, evidence and blockers live in
`.tmp/`.

## Outcome order

1. Make useful work easy to adopt: obtain, understand, authorize, run and stop
   a useful Flow.
2. Combine capable specialists: demonstrate reuse across applications and
   interoperability outside Jig.
3. Deliver a useful software factory: turn authorized issues into reviewable
   patches with executed tests and independent evidence, while people retain
   merge and release authority.
4. Let others build further capability: support independent builders and
   user-owned Starters based on demonstrated needs.

## Developer-alpha milestone

Complete: protected source, Linux host and native-client qualification gates
passed, and the qualified packages are publicly available. Published-package
factory adoption produced reviewable patches with executed repository tests and
independent acceptance cases. Bounded application-owned summary handoff is
implemented; it is not a new host subsystem.

This closes the developer-alpha launch milestone, not stable-interface promotion,
broad model reliability or comparative superiority. Exact revisions, artifacts,
evidence and supported limits belong in `.tmp/` and the public guides, not in
this roadmap.

## Next steps

1. Define a coherent host foundation for local adaptive artifact-producing
   applications: recoverable invocation, reusable file composition and controlled
   dependency-backed evaluation.
2. Qualify that supported envelope through maintainer-owned installed evidence
   and separate public-only consumers before release; external application teams
   must not wait through each host correction. Reuse delivered conversation,
   channel and retained-progress interfaces rather than duplicate them.

The [coordination inbox](inbox/) records the postponed contract-discovery and
conversation/handoff adoption work. Its entries are not implementation approval
or prerequisites for this completed launch.

## Workflow edit navigation

The [workflow editing job](../use-cases/JOB-001-locate-a-workflow-edit.md) has six use cases.
The proposed order starts with one decision and expands to changes that cross several ownership boundaries.

1. **Find one conditional reroute (UC-001).** Start with the existing inspection views.
   In Contact Import, follow `needs_mapping` from the converter to the importer's decision to export.
   Put the returned status, caller check, and next call within reach of the same source lookup.
   The editor should locate that decision, the ready route, and the earlier mapper refusal from the owner's request alone.
2. **Scope a change through shared code (UC-002, UC-003).** Show which call sites share a slot and which Bindings share an implementation.
   An editor should identify both post-edit chapter calls while preserving developmental and whole-book review.
   For a configuration change, the editor should locate the one Binding that selects the new target.
3. **Trace a changed result back to its decision owners (UC-005).** Follow the result through callers that forward, translate, or handle it.
   The editor should find the branch that acts on the result and identify which configured entrypoints depend on that decision.
   If a child's implementation is opaque, show how its caller would respond to a permitted result.
4. **Find the first write and the exits from repeated work (UC-004, UC-006).** Trace coordinated and directly requested exports to the first write.
   For repeated reviews, locate who schedules another pass, where rejection stops the work, and where approval rejoins publication.
   Where a choice is unresolved, preserve its known neighbors and point to its source.

Try each milestone on a held-out request in another application. Give unfamiliar editors ordinary source tools, topology, and contracts.
Compare what they identify with and without the focused behavior map before their first edit.
Record correct sites, missed alternatives, and unrelated files opened. If editors miss a connection, improve the point where they lost it.
Move on when they consistently find the owner and neighboring routes with little reconstruction.

## Ongoing proof

- Preserve the bounded outside-Jig unchanged-package consumption evidence;
  extend interoperability proof only for a concrete new claim.
- Keep adoption, native control, handoff and comparative-advantage claims tied
  to their distinct evidence. Neither a passing gate nor one small consumer
  establishes general reliability or superiority.
- Fix concrete release, CLI, authority and cleanup defects as found.

Use the doctrine's [decision test](../doctrine/design-judgment.md#the-decision-test)
before expanding scope. Postponed, untriaged tasks live in [`inbox/`](inbox/).
